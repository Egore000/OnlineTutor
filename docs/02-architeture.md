# Architecture

> Версия: 1.0  
> Статус: Утверждено  
> Документ: 02-architecture.md

---

# 1. Назначение документа

Документ описывает архитектуру проекта.

Архитектура утверждается до начала разработки и служит основным техническим ориентиром.

Изменения допускаются только при наличии объективной причины.

---

# 2. Архитектурные цели

Архитектура должна обеспечивать:

- простоту понимания;
- высокую скорость разработки;
- возможность масштабирования;
- независимость бизнес-логики от фреймворков;
- простоту тестирования;
- минимальное количество технического долга.

Приоритетом является разработка качественного MVP.

---

# 3. Архитектурный стиль

Проект использует модульную Clean Architecture.

Используются четыре слоя:

```
Presentation

↓

Application

↓

Domain

↓

Infrastructure
```

Каждый слой имеет строго определенную ответственность.

---

# 4. Правило зависимостей

Зависимости направлены только внутрь системы.

```
Presentation
      ↓
Application
      ↓
Domain

Infrastructure ───────► Domain
Infrastructure ───────► Application
```

Обратные зависимости запрещены.

---

# 5. Описание слоев

## Presentation

Отвечает за взаимодействие с пользователем.

Содержит:

- FastAPI Router
- HTTP Request
- HTTP Response
- Pydantic Schema
- Dependency Injection

Не содержит бизнес-логики.

---

## Application

Отвечает за выполнение пользовательских сценариев.

Содержит:

- Use Case
- DTO
- сервисы приложения

Именно здесь происходит оркестрация бизнес-процесса.

Application ничего не знает о FastAPI и PostgreSQL.

---

## Domain

Самый важный слой.

Содержит:

- Entity
- Value Object
- Repository Interface
- Domain Service
- Domain Exception

Domain не знает:

- FastAPI
- SQLAlchemy
- PostgreSQL
- OpenAI
- Docker

Domain полностью независим.

---

## Infrastructure

Отвечает за работу с внешним миром.

Содержит:

- SQLAlchemy
- Alembic
- Repository
- OpenAI
- файловое хранилище
- логирование
- кэш
- конфигурацию

Infrastructure реализует интерфейсы Domain.

---

# 7. Модули системы

На этапе MVP проект состоит из следующих модулей.

```
accounts/

students/

subjects/

materials/

lessons/

homework/

progress/

ai/

shared/
```

Каждый модуль максимально независим.

---

# 8. Структура модулей

Каждый модуль имеет одинаковую структуру.

```
module/

    application/

    domain/

    infrastructure/

    presentation/
```

Это позволяет легко ориентироваться в проекте.

---

# 9. Пример структуры

```
students/

    application/

        create_student.py

        update_student.py

        delete_student.py

    domain/

        entities.py

        repositories.py

        exceptions.py

    infrastructure/

        models.py

        repository.py

    presentation/

        router.py

        schemas.py
```

---

# 10. Shared Module

Общие компоненты находятся только здесь.

```
shared/

    config/

    database/

    security/

    logging/

    pagination/

    exceptions/

    utils/
```

Запрещается создавать второй Shared.

---

# 11. Почему не Feature First

Некоторые проекты используют структуру:

```
routers/

services/

repositories/

models/
```

При росте проекта она становится плохо масштабируемой.

Поэтому используется модульная структура.

---

# 12. Почему не микросервисы

Проект разрабатывается одним человеком.

Использование микросервисов:

- увеличит сложность;
- усложнит тестирование;
- усложнит деплой;
- замедлит разработку.

Используется модульный монолит.

---

# 13. Почему модульный монолит

Он позволяет:

- быстро разрабатывать;
- легко тестировать;
- выделить сервис позже при необходимости.

Каждый модуль должен быть максимально автономным.

---

# 14. Принцип работы запроса

Любой запрос проходит одинаковый путь.

```
HTTP Request

↓

Router

↓

Use Case

↓

Repository

↓

Database

↓

Repository

↓

Use Case

↓

Schema

↓

HTTP Response
```

Все запросы должны соответствовать данной схеме.

---

# 15. Repository Pattern

Доступ к данным осуществляется исключительно через Repository.

Запрещается обращаться к SQLAlchemy из Use Case.

Правильно:

```
UseCase

↓

Repository

↓

SQLAlchemy
```

Неправильно:

```
UseCase

↓

Session.execute(...)
```

---

# 16. Dependency Injection

Все зависимости внедряются извне.

Запрещается создавать объекты внутри Use Case.

Плохо:

```python
service = OpenAIService()
```

Хорошо:

```python
class CheckHomeworkUseCase:

    def __init__(self, ai_service):
        ...
```

---

# 17. Бизнес-логика

Вся бизнес-логика находится только в:

- Domain
- Application

Presentation содержит только HTTP.

Infrastructure содержит только техническую реализацию.

---

# 18. Работа с базой данных

Используется PostgreSQL.

ORM:

SQLAlchemy 2.

Миграции:

Alembic.

Прямой SQL допускается только если ORM значительно ухудшает производительность.

---

# 19. Работа с файлами

Все файлы проходят через единый File Storage.

На этапе MVP используется локальное файловое хранилище.

Замена на S3 должна требовать изменения только Infrastructure.

---

# 20. Работа с ИИ

ИИ рассматривается как внешний сервис.

Application не должен знать, используется:

- OpenAI;
- DeepSeek;
- локальная модель.

Используется интерфейс AI Service.

---

# 21. Конфигурация

Все настройки находятся в одном месте.

```
shared/config/
```

Запрещается читать переменные окружения в других местах проекта.

---

# 22. Логирование

Используется единая система логирования.

Логируются:

- ошибки;
- запуск приложения;
- HTTP-запросы;
- критические действия.

Не логируются:

- пароли;
- JWT;
- персональные данные;
- содержимое домашних заданий.

---

# 23. Обработка ошибок

Каждый слой отвечает только за свои ошибки.

Domain

↓

DomainException

Application

↓

ApplicationException

Presentation

↓

HTTPException

Запрещается выбрасывать HTTPException внутри Domain.

---

# 24. Аутентификация

Используется JWT.

Поддерживаются:

- Access Token;
- Refresh Token.

Все проверки пользователя выполняются в Presentation.

Use Case получает уже авторизованного пользователя.

---

# 25. API

Используется REST.

Формат данных:

JSON.

Версионирование:

```
/api/v1/
```

Даже первая версия должна использовать префикс версии.

---

# 26. Асинхронность

Backend полностью асинхронный.

Используются:

- async FastAPI
- async SQLAlchemy
- async Repository

Смешивать sync и async запрещается.

---

# 27. Тестирование

Предусматриваются три уровня тестов.

```
Unit

↓

Integration

↓

API
```

На MVP основной упор делается на Unit и Integration.

---

# 28. Безопасность

Минимальные требования.

- JWT
- хэширование паролей
- валидация данных
- CORS
- ограничения загрузки файлов
- защита приватных API

---

# 29. Принципы разработки

Во всём проекте соблюдаются следующие принципы.

## KISS

Предпочитать самое простое решение.

---

## YAGNI

Не реализовывать функции заранее.

---

## SOLID

Использовать там, где это действительно улучшает код.

Не превращать SOLID в самоцель.

---

## DRY

Не копировать одинаковую бизнес-логику.

---

## Explicit is better than implicit

Код должен быть максимально очевидным.

---

# 30. Архитектурные ограничения

Запрещается:

- создавать Generic Repository;
- создавать Base Service;
- создавать универсальный CRUD Service;
- использовать глобальные переменные;
- обращаться к БД минуя Repository;
- смешивать Domain и SQLAlchemy;
- писать бизнес-логику в Router.

# 32. Definition of Architecture Done

Архитектура считается реализованной, если:

- каждый модуль имеет одинаковую структуру;
- зависимости направлены внутрь;
- бизнес-логика отделена от инфраструктуры;
- отсутствуют циклические зависимости;
- все внешние сервисы изолированы Infrastructure;
- проект можно масштабировать без переписывания ядра.

---

# 33. Архитектурный принцип проекта

Главное правило разработки:

> **Проект должен оставаться простым настолько долго, насколько это возможно.**

Любое усложнение должно быть оправдано реальной потребностью, а не предположением о будущем развитии системы.
