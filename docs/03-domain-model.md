# 1. Назначение документа

Документ описывает предметную область проекта.

Он определяет:

- основные сущности;
- связи между ними;
- инварианты;
- агрегаты;
- Value Objects;
- правила изменения состояния.

Данный документ является основой для реализации:

- бизнес-логики;
- базы данных;
- REST API.

---

# 2. Принципы моделирования

При проектировании модели используются следующие правила.

## Простота

Модель должна отражать предметную область.

Она не должна отражать устройство базы данных.

---

## Один источник истины

Каждая бизнес-сущность существует только в одном месте.

---

## Минимум агрегатов

Создаются только те агрегаты, которые действительно защищают бизнес-инварианты.

---

## Минимум связей

Агрегаты взаимодействуют между собой через идентификаторы.

---

## MVP First

Не моделируются функции, отсутствующие в MVP.

---

# 5. Identity

## Назначение

Контекст отвечает за авторизацию пользователей.

В MVP поддерживается только один тип входа — email + пароль.

---

## Aggregate Root

```
Account
```

---

## Entity

### Account

Описание:

Аккаунт представляет учетную запись пользователя.

Он отвечает исключительно за аутентификацию.

---

### Поля

```
id

email

password_hash

is_active

created_at

updated_at
```

---

### Инварианты

Email уникален.

Пароль хранится только в виде хеша.

Удаление аккаунта запрещено при наличии связанных данных.

---

# 6. Users

## Aggregate Root

```
User
```

---

### Назначение

User представляет человека.

Это не ученик.

Не преподаватель.

Не родитель.

Просто пользователь платформы.

---

### Поля

```
id

account_id

first_name

last_name

phone

avatar

created_at

updated_at
```

---

### Инварианты

Каждый User принадлежит одному Account.

Один Account имеет только одного User.

---

# 7. Students

## Aggregate Root

```
Student
```

---

### Назначение

Student описывает образовательный профиль пользователя.

---

### Поля

```
id

user_id

notes

created_at

updated_at
```

---

### Почему Student отдельная сущность

Не каждый пользователь является учеником.

В будущем появятся:

Teacher

Parent

Administrator

Поэтому образовательная информация хранится отдельно.

---

### Инварианты

Student всегда связан с User.

Удаление Student запрещено при наличии занятий.

---

# 10. Lessons

## Aggregate Root

```
Lesson
```

---

### Назначение

Занятие между преподавателем и учеником.

---

### Поля

```
id

student_id

subject_id

title

description

starts_at

ends_at

status
```

---

### Статусы

```

completed

cancelled
```

---

### Инварианты

Время окончания больше времени начала.

Завершенное занятие нельзя перевести обратно в статус Planned.

Отмененное занятие нельзя завершить.

Удаление завершенного занятия запрещено.

---

### Связи

```
Lesson

↓

Student

↓

Subject
```

Все связи осуществляются через идентификаторы.

# 11. Value Objects

На первом этапе используются следующие Value Objects.

---

## Email

Содержит:

- адрес электронной почты;
- правила валидации;
- нормализацию.

---

## Phone

Содержит номер телефона.

Отвечает за форматирование и проверку.

---

## DateTimeRange

Используется для описания времени занятия.

Инвариант:

```
start < end
```

---

## FilePath

Инкапсулирует путь к файлу.

Не допускает хранения относительных путей неизвестного формата.

# 14. Homework

## Назначение

Контекст **Homework** отвечает за выдачу, выполнение и проверку домашних заданий.

В рамках MVP домашнее задание создаётся преподавателем после занятия и выполняется учеником.

---

## Aggregate Root

```
Homework
```

---

### Entity: Homework

Домашнее задание, выданное после конкретного занятия.

### Поля

```
id

lesson_id

title

description

due_at

status

created_at

updated_at
```

---

### Статусы

```
draft

assigned

completed

cancelled
```

---

### Инварианты

Домашнее задание всегда принадлежит одному занятию.

Домашнее задание нельзя выдать без занятия.

После перехода в статус `completed` изменение задания запрещено.

Дата сдачи должна быть позже даты выдачи.

---

## Aggregate Root

```
Submission
```

---

### Entity: Submission

Представляет выполненную учеником работу.

Submission является отдельным агрегатом, поскольку живёт собственной жизнью:

- отправляется;
- может быть переотправлена;
- проверяется преподавателем;
- анализируется ИИ.

---

### Поля

```
id

homework_id

student_id

comment

submitted_at

status
```

---

### Статусы

```
draft

submitted

checking

reviewed
```

---

### Инварианты

Submission всегда принадлежит одному Homework.

Submission нельзя изменить после начала проверки.

Ученик может иметь только одну активную Submission для одного Homework.

---

## Aggregate Root

```
Review
```

---

### Entity: Review

Результат проверки домашнего задания преподавателем.

---

### Поля

```
id

submission_id

score

feedback

ai_feedback

checked_at
```

---

### Инварианты

Review всегда принадлежит Submission.

Оценка находится в диапазоне от 0 до 100.

ИИ не может выставить окончательную оценку.

Поле `feedback` обязательно.

---

# 15. Progress

## Назначение

Контекст Progress предоставляет преподавателю и ученику информацию об успеваемости.

Данный контекст является производным.

Он не содержит уникальной бизнес-информации.

---

## Aggregate Root

```
Progress
```

---

### Entity: Progress

---

### Поля

```
id

student_id

completed_lessons

completed_homework

average_score

updated_at
```

---

### Инварианты

Progress существует только для Student.

Средний балл вычисляется автоматически.

Пользователь не может изменять Progress вручную.

# 16. AI

## Назначение

Контекст AI отвечает за интеграцию с искусственным интеллектом.

ИИ рассматривается исключительно как помощник преподавателя.

---

## Основные возможности

- анализ домашнего задания;
- генерация комментариев;
- рекомендации по оценке;
- предложения по улучшению задания;
- генерация похожих задач (в будущих версиях).

---

## Ограничения

ИИ:

- не изменяет данные самостоятельно;
- не принимает окончательных решений;
- не выставляет финальную оценку.

---

## AI Service

Domain содержит только интерфейс.

```
AIService
```

Infrastructure содержит реализацию.

Например:

```
OpenAIService

DeepSeekService

LocalLLMService
```

Application работает только через интерфейс.

# 22. Правила изменения модели

После утверждения Sprint 0 предметная модель считается стабильной.

Изменения допускаются только если:

- обнаружена ошибка моделирования;
- появилась новая бизнес-функция;
- существующая модель препятствует развитию проекта.

Запрещается изменять модель исключительно по причинам предпочтений в стиле реализации.

---

# 23. Принципы развития

При добавлении новых возможностей необходимо соблюдать следующие правила.

## Новые агрегаты

Добавляются только при наличии собственного жизненного цикла и инвариантов.

---

## Новые сущности

Добавляются только если не могут быть представлены существующими агрегатами.

---

## Новые Value Objects

Добавляются при наличии собственной логики валидации или поведения.

---

## Новые контексты

Создаются только если существующий контекст становится слишком большим или начинает отвечать за несколько независимых бизнес-задач.

---

# 25. Definition of Domain Model Done

Доменная модель считается завершённой, если:

- каждый бизнес-объект описан;
- определены агрегаты;
- определены инварианты;
- определены Value Objects;
- определены Repository Interfaces;
- определены Domain Services;
- определены Domain Events;
- отсутствуют циклические зависимости между агрегатами;
- взаимодействие агрегатов осуществляется только через идентификаторы.

---

# 26. Главный принцип предметной модели

Предметная модель должна описывать **реальный процесс обучения**, а не структуру базы данных или устройство пользовательского интерфейса.

Каждая сущность существует потому, что она отражает объект предметной области, а не потому, что её удобно хранить в таблице.

При возникновении сомнений приоритет всегда отдаётся простоте модели и понятности бизнес-логики.
