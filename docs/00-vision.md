# 1. Описание проекта

Проект представляет собой образовательную платформу для индивидуального и группового обучения, ориентированную в первую очередь на работу репетитора.

Главная идея проекта — не просто хранить домашние задания или расписание, а сопровождать весь образовательный процесс от первого знакомства с учеником до достижения поставленной учебной цели.

Платформа должна значительно сократить объем рутинной работы преподавателя за счет автоматизации и применения искусственного интеллекта, сохранив при этом полный контроль преподавателя над процессом обучения.

На первом этапе проект разрабатывается как личная система управления обучением (LMS + CRM), однако архитектура должна позволять в дальнейшем развить платформу в систему для небольшой онлайн-школы без переписывания ядра приложения.

---

# 2. Цели проекта

## Основная цель

Создать платформу, которая позволит преподавателю уделять больше времени обучению учеников и меньше — административной работе.

---

## Бизнес-цели

- увеличить количество учеников без увеличения нагрузки;
- повысить качество обучения;
- автоматизировать проверку домашних заданий;
- автоматизировать создание домашних заданий;
- централизованно хранить материалы;
- собирать статистику успеваемости;
- уменьшить количество ручной работы.

---

## Технические цели

Проект должен стать:

- удобным для поддержки;
- понятным для одного разработчика;
- масштабируемым без переписывания архитектуры;
- полностью типизированным;
- пригодным для промышленной эксплуатации.

---

# 3. Целевая аудитория

## Первый этап

Один преподаватель.

Платформа используется исключительно владельцем проекта.

---

## Второй этап

Несколько преподавателей.

Одна организация.

Общие ученики.

---

## Третий этап

Небольшая онлайн-школа.

Несколько преподавателей.

Несколько предметов.

Общий кабинет администратора.

---

# 4. Пользователи

## Преподаватель

Возможности:

- регистрация;
- управление учениками;
- управление расписанием;
- создание домашних заданий;
- проверка домашних заданий;
- загрузка материалов;
- просмотр статистики;
- использование ИИ.

---

## Ученик

Возможности:

- просмотр расписания;
- выполнение домашних заданий;
- прохождение тестов;
- просмотр материалов;
- просмотр прогресса;
- получение комментариев преподавателя.

---

## Родитель (не входит в MVP)

Планируется позже.

Будет иметь возможность:

- просматривать прогресс;
- видеть расписание;
- получать отчеты;
- оплачивать занятия.

---

## Администратор (не входит в MVP)

Появится после поддержки нескольких преподавателей.

---

# 5. Проблемы, которые решает проект

Сегодня преподаватель обычно использует несколько различных сервисов:

- Telegram;
- Google Calendar;
- Google Drive;
- Excel;
- PDF;
- ChatGPT.

В результате информация оказывается распределена по разным системам.

Проект объединяет все необходимые инструменты в одной платформе.

---

# 6. Основные возможности MVP

## Управление пользователями

- регистрация;
- авторизация;
- профиль пользователя.

---

## Ученики

- список учеников;
- карточка ученика;
- поиск;
- архив.

---

## Расписание

- создание занятия;
- перенос;
- отмена;
- просмотр календаря.

---

## Домашние задания

- создание;
- сдача;
- прикрепление файлов;
- комментарии преподавателя;
- статусы выполнения.

---

## Материалы

- загрузка PDF;
- загрузка изображений;
- ссылки;
- группировка по предметам.

---

## Искусственный интеллект

Первая версия ИИ:

- помощь в проверке домашних заданий;
- генерация комментариев;
- рекомендации преподавателю.

ИИ не принимает окончательных решений.

Финальная оценка всегда остается за преподавателем.

---

# 7. Что НЕ входит в MVP

Сознательно исключаются следующие функции:

- видеозвонки;
- собственный чат;
- мобильное приложение;
- онлайн-оплата;
- поддержка нескольких организаций;
- конструктор курсов;
- маркетплейс преподавателей;
- публичный каталог курсов;
- внутренняя социальная сеть;
- система сертификатов.

Каждая из этих функций может быть добавлена позже отдельным модулем.

---

# 8. Основные принципы разработки

## MVP First

Проект должен начать приносить пользу как можно раньше.

Каждая новая функция должна иметь практическую ценность.

---

## Простота

Предпочтение отдается простым решениям.

Сложность допускается только при наличии объективной необходимости.

---

## Минимум абстракций

Запрещается создавать универсальные решения "на будущее".

Каждая абстракция должна решать существующую проблему.

---

## Масштабируемость

Архитектура должна позволять:

- добавить второго преподавателя;
- добавить организацию;
- добавить новые предметы;

без переписывания существующего кода.

---

## Чистый код

Код должен быть:

- читаемым;
- типизированным;
- протестированным;
- документированным.

---

# 9. Ограничения проекта

На первом этапе предполагается:

- один разработчик;
- один преподаватель;
- ограниченное время разработки.

Поэтому скорость разработки имеет высокий приоритет.

Любое архитектурное решение должно быть оправдано.

---

# 10. Ключевые сценарии использования

## Сценарий №1

Преподаватель создает занятие.

↓

Назначает домашнее задание.

↓

Ученик выполняет домашнее задание.

↓

Преподаватель получает уведомление.

↓

Проверяет работу.

↓

Ученик получает комментарий.

---

## Сценарий №2

Преподаватель загружает материалы.

↓

Ученик открывает материалы.

↓

Изучает тему.

↓

Выполняет домашнее задание.

---

## Сценарий №3

Преподаватель отправляет работу на ИИ-проверку.

↓

ИИ анализирует решение.

↓

Формирует рекомендации.

↓

Преподаватель принимает окончательное решение.

---

# 11. Критерии успешного MVP

MVP считается успешным, если преподаватель сможет полностью отказаться от использования сторонних сервисов для ведения учеников.

Минимальный набор возможностей:

- хранение учеников;
- ведение расписания;
- работа с домашними заданиями;
- хранение материалов;
- помощь ИИ при проверке домашних заданий.

---

# 12. Долгосрочное развитие

После успешного завершения MVP возможно развитие проекта в следующих направлениях:

- поддержка нескольких преподавателей;
- кабинет родителя;
- аналитика обучения;
- система оплаты;
- мобильное приложение;
- полноценный ИИ-ассистент;
- онлайн-школа;
- SaaS-платформа для репетиторов.

---

# 13. Архитектурные принципы проекта

Для всего проекта принимаются следующие решения:

1. Backend — FastAPI.
2. PostgreSQL в качестве основной БД.
3. SQLAlchemy 2.0.
4. Alembic для миграций.
5. Clean Architecture без избыточных абстракций.
6. Строгая типизация.
7. Docker для локальной разработки.
8. REST API.
9. ИИ интегрируется через отдельный сервисный слой.
10. После утверждения Sprint 0 архитектура считается стабильной и изменяется только при объективной необходимости.

---

# 14. Definition of Success

Проект считается достигшим первоначальной цели, если:

- преподаватель полностью ведет обучение через платформу;
- количество ручной работы существенно сократилось;
- домашние задания проверяются быстрее;
- все материалы находятся в одном месте;
- ученик получает понятный и удобный интерфейс обучения;
- архитектура позволяет без переписывания ядра перейти к поддержке нескольких преподавателей.
